## Análisis y correcciones mínimas

### CI-01 — Validar entrada, procedencia y elegibilidad productiva

En ambos workflows, el camino manual entra en else y solo comprueba conclusion de workflow_runs[0]. Un Quality Gates manual exitoso sobre una rama feature satisface ese predicado y autoriza el checkout de ese SHA para Production. El chequeo head_branch == main está exclusivamente en workflow_run. La declaración environment: Production no demuestra que existan restricciones remotas configuradas ni valida por sí misma la pertenencia del commit.

Además, target_sha se inserta directamente en el texto de run. Bash puede interpretar sustituciones o comillas aportadas en el input antes de validarlo. Este vector requiere capacidad de dispatch; no se afirma explotación anónima ni se ejecutó payload sobre GitHub.

Corrección: pasar valores por env, no interpolar inputs en el programa; admitir exclusivamente SHA completo hexadecimal de 40 caracteres; rechazar ramas, expresiones, saltos de línea y metacaracteres. En los dos eventos exigir repositorio de origen confiable, workflow esperado, SHA exacto, resultado success y política productiva main. Verificar pertenencia del SHA a main (o a su historia si se permiten rollbacks) y que la evidencia corresponde al árbol realmente compilado. Una aprobación de PR/feature no autoriza producción. Registrar run_id/run_attempt y SHA autorizado. No asumir existencia de protecciones remotas no inspeccionadas.

### CI-02 — Corregir sintaxis del condicional

En frontend línea 30 usar una expresión envuelta, por ejemplo:

```yaml
if: ${{ !(github.event_name == 'pull_request' && github.event.action == 'closed') }}
```

Validar con un parser de YAML y un validador de workflows antes de correr los tests del contrato. La comprobación por includes no detecta este defecto.

### CI-03 — Ordenar QG y preview, conservando el SHA probado

El evento pull_request dispara ambos workflows; no existe dependencia entre ellos. Si la consulta ocurre antes de finalizar QG, el preview termina bloqueado aunque QG pase después. workflow_run solo escucha main, por lo que la finalización de un QG de feature no recupera automáticamente ese preview. No confundir este bloqueo seguro con un flujo funcional.

Elegir una única estrategia: dependencia mediante workflow reutilizable/jobs, continuación tras el run pertinente o espera acotada que contemple estado pendiente y termine al vencer el plazo. Documentar si se prueba/despliega head o merge y usar exactamente el mismo árbol. QG actual usa checkout por defecto y, en pull_request, GitHub prepara el merge; el deploy actual elige head. No presentar head_sha de la API como prueba suficiente del checkout realizado. Conservar política segura para forks y no otorgarles secretos de despliegue para resolver el bloqueo.

### CI-04 — Separar GitHub Environment de destino Azure

Mantener environment: Production/Preview como contexto de GitHub, pero corregir los inputs de Azure. El parámetro deployment_environment no es una etiqueta de permisos: selecciona un named preview. Para producción usar el destino productivo según el contrato de la acción, sin un nombre de preview, con política production_branch cuando corresponda. Para previews usar el entorno nativo por número de PR o nombres únicos coherentes por PR. La operación close debe apuntar al mismo entorno que upload y no afectar otros PRs.

No se desplegó ni se verificó configuración del portal Azure; este hallazgo deriva del YAML y del contrato oficial del proveedor, no de una supuesta observación remota.
