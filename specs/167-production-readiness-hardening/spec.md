# Feature Specification: Production Readiness Hardening

**Feature Branch**: `167-production-readiness-hardening`

**Created**: 2026-07-06

**Status**: Draft

**Input**: User description: "Bring OneITB from 92% to 100% with zero technical debt, using Speckit, auditing contracts, closing remaining roadmap features, adding quick wins, and preparing an academic production-readiness report."

## User Scenarios & Testing

### User Story 1 - Observable Backend Runtime (Priority: P1)

As a maintainer preparing the project for final review, I need backend requests and GraphQL failures to be traceable by a stable correlation identifier so runtime issues can be investigated without guessing.

**Why this priority**: The roadmap still marks logging, metrics, and error traceability as pending. This can be improved without adding external infrastructure or secrets.

**Independent Test**: Start the backend, execute a GraphQL request, and confirm the response contains an `X-Correlation-ID` header while backend logs include the same identifier.

**Acceptance Scenarios**:

1. **Given** a client sends a request without a correlation header, **When** the backend handles it, **Then** the response includes a generated correlation identifier and logs the request outcome with that identifier.
2. **Given** a client sends `X-Correlation-ID`, **When** the backend handles it, **Then** the same valid identifier is returned and used in structured log scope.

---

### User Story 2 - GraphQL Metric Fields Without N+1 (Priority: P1)

As an administrator or feed reader, I need user and report metrics to render without producing one SQL query per object in a list.

**Why this priority**: Current GraphQL computed fields for social metrics are useful but can degrade quickly in admin/feed lists.

**Independent Test**: Execute queries that request `users.totalPosts`, `users.totalComments`, `users.totalLikesReceived`, `users.totalReportsReceived`, and `inquiries.reportCount`; confirm grouped/batched loading is used instead of per-parent count queries.

**Acceptance Scenarios**:

1. **Given** a list query returns multiple users, **When** metric fields are selected, **Then** counts are loaded through batched grouped queries.
2. **Given** a list query returns multiple inquiries, **When** `reportCount` is selected, **Then** report counts are loaded through a batched grouped query.

---

### User Story 3 - Honest Production Readiness Evidence (Priority: P2)

As the project owner, I need a final report that separates implemented, verified, and blocked work so the academic presentation does not overclaim readiness.

**Why this priority**: The project is close to completion, but roadmap completion requires runtime/browser and infrastructure evidence for remaining gaps.

**Independent Test**: Review the evidence and documentation updates; each remaining gap must be tied to a concrete validation or infrastructure blocker.

**Acceptance Scenarios**:

1. **Given** a feature cannot be verified in this environment, **When** the spec closes, **Then** the blocker is recorded explicitly and roadmap status is not inflated.
2. **Given** source changes were made, **When** validation runs, **Then** commands and outcomes are recorded in `evidence.md`, `DEVELOPMENT_LOG.md`, and `DOCUMENTATION_STATUS.md`.

### Edge Cases

- If NuGet restore remains blocked, host build and EF model checks must stay blocked rather than reported as verified.
- If browser/runtime services are not running, UI regressions must stay pending.
- Distributed pub/sub and shared file storage must not be represented as complete without an actual transport/storage implementation.

## Requirements

### Functional Requirements

- **FR-001**: System MUST emit and propagate a correlation identifier for HTTP requests.
- **FR-002**: System MUST include request method, path, status code, elapsed time, and correlation identifier in backend logs.
- **FR-003**: GraphQL user metric fields MUST avoid per-parent count queries in list responses.
- **FR-004**: GraphQL inquiry report count MUST avoid per-parent count queries in list responses.
- **FR-005**: Documentation MUST distinguish implemented work, verified work, and blocked work.
- **FR-006**: The roadmap MUST only mark additional items complete when there is fresh evidence.
- **FR-007**: The final academic report MUST summarize executed work, files affected, validations, and residual risks.

### Key Entities

- **Correlation Identifier**: Request-level identifier accepted from `X-Correlation-ID` or generated by the server.
- **Metric Count**: Aggregated count for user posts, comments, likes received, reports received, and inquiry reports.
- **Evidence Record**: Spec-local record of commands executed, results, and blockers.

## Success Criteria

### Measurable Outcomes

- **SC-001**: Every backend HTTP request handled by the app returns exactly one correlation identifier header.
- **SC-002**: Metric fields for lists use batched grouped loading instead of one query per returned item.
- **SC-003**: At least one roadmap quality item is either completed with evidence or explicitly left blocked with the concrete reason.
- **SC-004**: The final report can be attached directly to the academic audit package without extra reconstruction.

## Assumptions

- Existing .NET, HotChocolate, EF Core, Apollo, and Tailwind dependencies remain unchanged.
- No external Redis, cloud storage, browser session, or package download is assumed available during this spec.
- Host .NET validation may require a network restore due the current NuGet boundary recorded in spec 166.
