# Plan de integración de la Spec 220

Base y límites figuran en audit.md. contracts.graphql es un delta de diseño. Los nombres de operaciones existentes deben conservarse y Local AGY debe componer el delta con el esquema ejecutable antes de generar documentos Apollo. Los DTO devueltos a un consumidor externo deben exponer campos explícitos, nunca colecciones EF navegables por defecto.

### CV entregado y gestión laboral

1. Usar CapturedApplicationCv.From del directorio domain como proyección pura sobre un agregado completo leído por ApplicantId de claims. Incluir Account, carreras y cinco colecciones ordenadas. La versión es un hash del mismo JSON UTF-8 que se almacena. Comparar contra expectedCvVersion en el servidor. La hora de la captura se conserva separada para que las vistas previas repetidas sean comparables. La versión es un control de edición, nunca una credencial.
2. Agregar JobApplicationCv con ApplicationId como PK/FK explícita única hacia JobApplication y DeleteBehavior.Restrict, SchemaVersion, CapturedAtUtc y PayloadJson con check ISJSON. Excluir PayloadJson y navegaciones EF del esquema. Mantener nulas las capturas de postulaciones previas. Desplegar primero la tabla, después el servicio y finalmente el cliente. Un downgrade debe conservar las capturas mientras existan lectores de la versión anterior.
3. En applyWithCv comprobar rol, cuenta activa, oferta activa y propietario de los datos desde claims. Leer el agregado coherentemente y persistir postulación, captura y evento de notificación en una transacción SQL. Una lectura fragmentada bajo READ COMMITTED puede mezclar ediciones entre secciones. Usar una transacción con aislamiento que asegure la misma versión de los datos hasta guardar y reintento acotado de conflictos transitorios. Usar el índice único existente para arbitrar carreras. Una repetición con la misma captura devuelve la aplicación ya creada; una versión distinta no sobrescribe la anterior. Un fallo al publicar el aviso no debe convertir una candidatura guardada en un error ambiguo de reintento.
4. applicationCv y employmentApplication deben comprobar que quien consulta sea el postulante o el titular de la oferta. El administrador que no es titular conserva el límite observado. Eliminar del contrato laboral cualquier vía al CV vivo u oculto, incluido JobApplication.applicant a través de la consulta histórica y las selecciones anidadas. Conservar los campos históricos necesarios con resolvers explícitos y proyección autorizada. Ejercitar selecciones arbitrarias contra el esquema, no solo el fragmento de jobs.js.
5. JobBoard abre una confirmación con el CV guardado y el nombre de la oferta. EmployerJobOffers carga la captura al abrir el candidato, la adapta a CVData y usa CVATSPrintTemplate para lectura/impresión. Probar texto extraíble, orden y saltos de página con una captura que incluya proyectos e idiomas. El componente no debe leer userProfile para suplir una captura ausente.

### Adjuntos de chat

1. Extender POST /api/upload con propósito privado explícito conservando el flujo de publicaciones. Reusar validación de extensión, tamaño real, tipo declarado, inspección de estructura y nombres generados. El resultado privado es un uploadId opaco. Nunca devolver un identificador de storage accesible como archivo estático. En modo local guardar fuera de wwwroot; en el proveedor remoto exigir objetos privados o rechazar el modo.
2. PrivateUpload registra Id, OwnerId, StorageKey, nombre de presentación saneado, MIME verificado, bytes y ExpiresAtUtc. MessageAttachment tiene MessageId, UploadId, orden, FKs Restrict e índice único UploadId. Message añade ClientMessageId nullable e índice único filtrado por (SenderId,ClientMessageId). El texto sigue siendo string y se guarda vacío solo cuando la colección validada contiene archivos. No poblar filas antiguas.
3. sendPrivateMessage recibe IDs, nunca URLs ni senderId. En una transacción verificar destinatario permitido, propietario, caducidad, estado libre y límites agregados; crear mensaje y consumir cada upload una sola vez. Repetición idéntica devuelve el mismo ID. Una repetición con otro receptor, texto o adjuntos devuelve conflicto. La decisión debe ser segura bajo envíos paralelos y rollback. Retirar objetos vencidos y huérfanos mediante barrido acotado que no pueda borrar archivos recién vinculados. Para el push fallido después de commit, reconciliar por historial/ID al reconectar.
4. Extender conversation, searchMyMessages, sendMessage y messageReceived para resolver la colección desde el mismo DTO. Para el historial paginado usar lote por IDs; para el evento usar el mensaje ya confirmado con adjuntos. GET autenticado /api/message-attachments/{id} debe resolver adjunto → mensaje → remitente/receptor activo en cada acceso, devolver respuesta opaca a un tercero y Cache-Control privado/no-store. Proteger previews y peticiones parciales igualmente. En React usar fetch con bearer y object URL de vida limitada o URL privada de corta duración; no incluir JWT en URL. Revocar object URLs en desmontaje, cambio de cuenta y sustitución del archivo.
5. Compartir compositor y burbuja entre PrivateChat y MiniChatWidget. Permitir cancelar una carga, conservar borrador ante error, distinguir «subiendo» de «enviado» y deduplicar optimistic/HTTP/WebSocket. «Adjunto» sirve como vista previa textual para un mensaje sin texto. messagingPeer debe devolver un contacto mínimo activo y respetar la misma política que iniciar conversación.

### Muro y comentarios

Aplicar primero el parche adjunto. Mantener getInquiriesPage, el filtro de visibilidad efectivo y el borrado lógico. Para hilos grandes añadir una query acotada de raíces y respuestas con cursor y una búsqueda de contexto por commentId que devuelve su raíz. Aplicar el mismo predicado de visibilidad antes de listar, responder, reaccionar o reportar. Un ID retirado debe devolver el mismo estado que uno ajeno. Conservar un nivel de respuestas con menciones dirigidas y evitar duplicar arrays de comentarios en la caché del feed y detalle.

Extender CommunityReport con CommentId nullable, FK Restrict. Conservar InquiryId para los reportes existentes y obtenerlo del comentario en el servicio. Asegurar la pertenencia con FK compuesta (CommentId, InquiryId) a clave alternativa (Id, InquiryId) de Comment. Reemplazar el índice único de reportes abiertos por índices filtrados separados para la publicación y el comentario. reportComment no acepta un ID de publicación aportado por el cliente. ReportModal muestra el objeto real. Sustituir el cero fijo de Comment.reportCount por un DataLoader agregado, conservando la política del contador de publicaciones.

### Comisiones, notas y regularidad

* CourseSection(Id, SubjectId, Term, Code), clave única (SubjectId, Term, Code). SectionInstructor(SectionId, ProfessorId) y SectionEnrollment(SectionId, StudentId) con claves compuestas. Para administrar padrones, importar asignaciones desde una fuente autorizada o habilitar mantenimiento por Administrador con audit log. Un Profesor no se autoasigna. En pruebas usar fixtures explícitos. Aplicar alcance por comisión en padrón, recursos específicos y calificación; no inferir cursada a partir de UserCareer.
* SectionGrade(Id, SectionId, StudentId, AssignedById, Score, Status, UpdatedAtUtc, RowVersion) con FK compuesta al padrón e índice único (SectionId, StudentId). Conservar AcademicProgress como resumen/legado por materia y separar nuevos intentos por comisión. La misma transacción escribe el intento y la proyección de resumen conforme a una regla explícita de precedencia académica. Definir con la institución qué intento alimenta el resumen; hasta entonces mostrar los intentos por separado y preservar el dato histórico. Evitar que el endpoint legado o un mock SIU escriban una nota de comisión eludiendo autorización/control de versión. Incluir el ID de sección en importaciones nuevas y rechazar datos ambiguos.
* EnrollmentStanding(Id, StudentId, CareerId, Term, Source, SourceReference, Status, ValidFromUtc, ValidUntilUtc, RevokedAtUtc) asienta evidencia institucional real. RegularStudentCertificate(Id, StandingId, IssuedAtUtc, ValidUntilUtc, nombre y carrera a emisión) con FK Restrict. Reutilizar constancia vigente de la misma acreditación bajo solicitudes concurrentes. Al abrirla comprobar vigencia y revocación. issueRegularStudentCertificate usa claims del alumno. Un tercero no puede obtenerla por ID. No exponer notas, email o DNI en una nueva consulta pública. Conservar publicCertificate(id) para la materia aprobada y etiquetar la exportación actual como progreso.
* Migración expansiva, sin reasignar notas viejas ni crear comisiones ficticias. Validar índices en SQL Server 2022, FKs explícitas, rowversion y ausencia de shadow properties. Las pruebas InMemory no verifican esos invariantes. Revisar script SQL generado y plan de reversión preservando datos antes de aplicar solo a la base de pruebas.
